# Паралельне обчислення суми елементів масиву

## Опис завдання

Реалізація програми обчислення суми елементів масиву з **1 000 000 000** (1 мільярд) елементів із використанням багатопоточності на трьох мовах програмування: **Java**, **C#** та **Go**.

Для кожної мови реалізовано декілька підходів до багатопоточності — від базових (ручне створення потоків) до "просунутих" (ForkJoinPool, PLINQ, атомарні операції). Усі реалізації порівнюються з однопоточним базовим методом.

## Інструкції з запуску

### Java

```bash
cd Java
javac ParallelSum.java
java -Xmx8g ParallelSum                    # масив 1 млрд, авто-кількість потоків
java -Xmx8g ParallelSum 100000000          # масив 100 млн
java -Xmx8g ParallelSum 1000000000 8       # масив 1 млрд, 8 потоків
```

### C#

```bash
cd CSharp
dotnet build -c Release
dotnet run -c Release                       # масив 1 млрд
dotnet run -c Release -- 100000000          # масив 100 млн
dotnet run -c Release -- 1000000000 8       # масив 1 млрд, 8 потоків
```

### Go

```bash
cd Go
go build -o parallel_sum.exe parallel_sum.go
./parallel_sum.exe                          # масив 1 млрд
./parallel_sum.exe -size 100000000          # масив 100 млн
./parallel_sum.exe -workers 8              # конкретна кількість горутин
```

## Аналіз ефективності

### 1. Порівняння однопоточних реалізацій

| Мова | Час однопоточного (мс) |
|------|------------------------|
| Java | 173.70 |
| C#   | 398.07 |
| Go   | 535.35 |

Java показує найкращу однопоточну продуктивність — **у 2.3× швидше за C#** та **у 3.1× швидше за Go**. Це пояснюється агресивною JIT-оптимізацією HotSpot JVM, яка ефективно розгортає цикли, векторизує операції та оптимізує доступ до масивів. C# CLR також має JIT, але менш агресивний для таких примітивних операцій. Go компілюється AOT (ahead-of-time), і його компілятор менш агресивно оптимізує числові цикли.

### 2. Аналіз Java-реалізацій

**Найкращий результат**: Manual Threads з 4 потоками — **91.40 мс (1.90×)**.

| Ранг | Метод | Час (мс) | Прискорення |
|------|-------|----------|-------------|
| 1 | Manual Threads (4) | 91.40 | 1.90× |
| 2 | ExecutorService (4) | 92.48 | 1.88× |
| 3 | ExecutorService (8) | 94.36 | 1.84× |
| 4 | Manual Threads (12) | 96.75 | 1.80× |
| 5 | ExecutorService (12) | 97.99 | 1.77× |
| 6 | Manual Threads (8) | 98.00 | 1.77× |
| 7 | ForkJoinPool | 104.39 | 1.66× |
| 8 | Manual Threads (2) | 105.87 | 1.64× |
| 9 | Parallel Stream | 107.25 | 1.62× |

**Ключові спостереження:**

- **Manual Threads vs ExecutorService**: обидва підходи показують подібну продуктивність. При 4 потоках Manual Threads має мінімальну перевагу (91.40 vs 92.48 мс) завдяки відсутності накладних витрат на управління пулом.
- **Стеля масштабування при 4 потоках**: збільшення кількості потоків з 4 до 8 або 12 **не дає приросту**, а навіть дещо погіршує результат. Це класична ознака **memory-bound** задачі.
- **ForkJoinPool**: показує гірший результат через накладні витрати на рекурсивне розбиття задач та створення об'єктів `RecursiveTask`. Цей механізм ефективніший для обчислювально інтенсивних рекурсивних задач.
- **Parallel Stream**: працює через ForkJoinPool, має додатковий overhead на boxing та стрім-пайплайн.

**Ключові спостереження:**

- **Task і Thread** — найефективніші. `Task<long>` — рекомендований підхід у сучасному .NET, оскільки використовує пул потоків і показує найкращий результат (105.43 мс).
- **Масштабування в C# краще, ніж у Java**: прискорення зростає від 1.48× (2 потоки) до 3.78× (12 потоків), тоді як у Java стеля на рівні 1.90×. Це пояснюється тим, що .NET CLR менш агресивно оптимізує однопоточний код, залишаючи більше "простору" для паралельного прискорення.
- **Parallel.For повільний для простих операцій**: навіть з оптимальним паттерном `localInit`/`localFinally` + `Interlocked.Add`, накладні витрати значні для тривіальної операції додавання (288.42 мс — майже в 3× повільніше за TaskSum).
- **PLINQ — найповільніший**: LINQ-конвеєр з `Select(x => (long)x)` створює значний overhead через партиціонування та обробку елементів. При 687.47 мс він навіть **повільніший за однопоточний baseline** (0.58×).

- **Mutex-підхід дещо швидший за канали та атомарні операції** при 8 горутинах. Це пояснюється тим, що м'ютекс захоплюється лише один раз на горутину (після обчислення локальної суми), а додатковий overhead каналів (буферизація, планування) та атомарних операцій (бар'єри пам'яті) мають вищу ціну.
- **Стеля масштабування при 8 горутинах**: збільшення з 8 до 12 горутин не дає приросту — результати практично ідентичні (100.43 vs 100.67 мс). Пропускна здатність пам'яті вичерпана.
- **Горутини — надзвичайно легковагі**: створення тисяч горутин не має помітного overhead порівняно з потоками ОС у Java та C#.

### 5. Порівняння найкращих результатів Java vs C# vs Go

| Параметр | Java | C# | Go |
|----------|------|-----|-----|
| Метод | Manual Threads (4) | TaskSum (12) | goroutineMutexSum (8) |
| Абсолютний час | **91.40 мс** | 105.43 мс | 100.43 мс |
| Прискорення відносно baseline | 1.90× | 3.78× | **5.33×** |

- **Java швидша в абсолютних числах** (~8% швидше за Go, ~14% швидше за C#) завдяки кращій JIT-оптимізації.
- **Go на другому місці** за абсолютним часом (100.43 мс), випереджаючи C# (105.43 мс), незважаючи на найповільніший однопоточний baseline.
- **Go демонструє найкраще відносне прискорення** (5.33×), оскільки однопоточна версія найповільніша, а горутини масштабуються ефективніше завдяки легковагому плануванню.
- **Усі три мови досягають схожого абсолютного мінімуму** (~91–105 мс), що підтверджує обмеження пропускною здатністю пам'яті.

### 6. Чому обмежене прискорення? (Memory-Bound задача)

Сумування масиву — це **задача, обмежена пропускною здатністю пам'яті** (memory-bound). Кожен елемент читається з RAM один раз, а операція над ним тривіальна (одне додавання).

```
Теоретична пропускна здатність DDR4 dual-channel ≈ 40–50 ГБ/с
Масив 1 млрд × 4 байти = 4 ГБ
Мінімальний час зчитування ≈ 4 ГБ / 50 ГБ/с ≈ 80 мс
```

Це пояснює, чому навіть з 12 потоками/горутинами прискорення далеко від лінійного (12×): усі потоки конкурують за спільну шину пам'яті. Найкращі результати всіх трьох мов (91–105 мс) наближаються до теоретичного мінімуму в ~80 мс, що підтверджує, що саме пропускна здатність пам'яті є головним обмежуючим фактором.

## Загальні висновки

1. **Ручне управління потоками** (`Thread` / горутини) дає найкращу продуктивність для простих задач завдяки мінімальним накладним витратам.

2. **Пули потоків** (`ExecutorService`, `Task`) — оптимальний компроміс між продуктивністю та зручністю. Рекомендовані для промислового коду.

3. **Високорівневі абстракції** (`Parallel.For`, PLINQ, `Parallel Stream`) — зручні для написання, але мають значний overhead для простих обчислень. Ефективніші для складних задач з великим обсягом обчислень на елемент.

4. **ForkJoinPool** ("розділяй і владарюй") — ефективний для рекурсивних задач із нерівномірним навантаженням, але надмірний для лінійного сумування.

5. **Горутини Go** — найлегковагніший механізм паралелізму серед трьох мов. Незважаючи на найповільніший однопоточний код, Go досягає найкращого відносного прискорення (5.33×) та конкурентного абсолютного часу.

6. **Оптимальна кількість потоків** для memory-bound задач зазвичай обмежена кількістю каналів пам'яті (2–4), а не кількістю ядер CPU. Це підтверджується тим, що в Java стеля досягається при 4 потоках, а в C# та Go — при 8–12.

7. **Memory-bound обмеження** — ключовий фактор, який стримує масштабування. Усі три мови досягають схожого абсолютного мінімуму (~91–105 мс), що близько до теоретичної межі пропускної здатності пам'яті (~80 мс).
